# 跨网互联

## 经 A 访问局域网

在「共享栏目 → 跨网互联 → 网段互联」输入跳板机 A 的 IPv4，点「读取 A 的网段」。DevKit 在 A 上时读取本机接口和路由表，在其他设备上时通过已核对指纹的 SSH 档案读取 A。首次使用远程 A 可在桌面补录账号。有编辑和检测权限的共享网页也可查看网段，读取远程 A 另需 SSH 终端权限。

在访问电脑上打开 DevKit，读取 A 后点 **「一键接入」**。DevKit 装在 A 上时，先填写要接入的电脑地址，首次管理远程设备需在页面核对 SSH 指纹并提供管理账号。默认「自动选择」会检查访问电脑到 A 的路由：同一链路上配置直连路由；隔着其他网关则准备 WireGuard、启动两端隧道并检查握手。系统请求管理员授权时按提示确认。远程 Windows 账号需有管理员权限，远程 Linux 账号需有 root 或免交互 sudo 权限。

接入就绪后，在访问电脑上用目标设备原来的 IP 和端口打开服务。直连模式需要目标侧网关已有返回访问电脑的路由。三层隧道需要访问电脑能连到 A 的 UDP 端口（默认 51820）；DevKit 会使用本机已安装的 WireGuard，或从 Windows 官方安装包、Linux 发行版软件源提取临时工具。Linux A 还需支持 WireGuard 转发和 iptables。站点防火墙、上游 NAT 和业务服务的访问控制继续生效。

**「取消部署」** 在部署中和接入后都可用。DevKit 等当前系统操作结束，然后按相反顺序移除本次创建的路由、隧道、临时文件及地址转换，恢复接口转发。失败会触发同一恢复流程。若设备离线，页面会指出待恢复的设备和步骤；恢复管理连接后点「重试取消部署」。重新打开网段页面仍可操作先前的部署。要为其他设备手工部署，可选择「直连网关」或「三层隧道」导出配置包。

例如，A 能访问 B 侧的 `192.168.10.0/24`、C 侧的 `192.168.20.0/24`，并有一条通往 `10.40.0.0/16` 的静态路由。核对「目的网段」后，在桌面按接入位置导出。默认列出 A 的 IPv4 接口网段，以及 Linux 主路由表或 Windows 活动路由表中的显式单播前缀。A 依靠默认网关或策略路由访问的内网可手动补入，例如 `10.50.0.0/16`。本功能处理 IP 单播，服务仍使用各自的身份验证。

| 访问端与 A 的位置 | 部署方法 | 回复怎样返回 |
| --- | --- | --- |
| A 在本地链路上，可作为下一跳 | 导出「网关路由」。在 A 开启转发，B、C 侧各自选取以本侧 A 地址命名的 `via-` 目录。要让整个 LAN 主动访问，可将对应前缀和下一跳配置到现有 LAN 网关；也可只在访问端运行脚本。 | 在目标侧网关添加返回来源网段的路由，使用本侧 A 的地址作下一跳。如果默认网关就是 A，已有回程。 |
| B 或 C 经其他网关连接 A | 选择「三层隧道」。安装 WireGuard，在 A 和相应客户端分别启用自己目录里的配置。A 的 UDP 端口默认 51820，须能从接入端到达。Linux A 还需要 iproute2、sysctl 与 iptables，Windows A 可使用 WinNAT。 | A 的 `forward.sh` 或 `forward.ps1` 为隧道来源配置转发和 SNAT，目标主机向 A 回包。发现不兼容的 WinNAT 时，脚本在启用转发前停止。沿用现有 NAT 或改用回程路由时，需单独启用 A 相关接口的转发，并核对目标侧回程。 |

直连配置按 A 的实际出口和最长匹配前缀生成。若 A 的直连网段中有更具体的前缀经其他网关或 VPN 可达，普通客户端会为该前缀添加经 A 的路由。若安装脚本的设备本身就是 A 到某前缀的下一跳，它会保留自己的去程。手工配置硬件网关时，对照脚本每行的目的前缀与后续列出的下一跳地址，跳过含本机地址的行。

两种接入方式可同时使用，例如 B 使用直连路由，C 使用隧道。A 对两侧使用不同入口且隔着 NAT 时，在相应客户端的 `Endpoint` 填入实际可达的地址和映射后的 UDP 端口，并让入口走原有链路。可在导出前排除客户端本地优先的前缀；若两侧使用了相同的主机地址，要通过改址或地址转换消除歧义。部署包内有对应平台的启用步骤。Linux 直连路由脚本设置当前运行状态，需要跨重启时应在对应网络管理器保存路由和转发配置。

重新读取 A 时会排除 DevKit 自己的 `devkit-a` 接口及其路由。已有隧道地址段与现场网段仍兼容时，重新导出会沿用该地址段。A 的转发脚本先检查所需接口、隧道和 NAT；应用中途失败时，会尝试恢复本次改动的转发状态。

隧道包包含 A、B、C 各自的私钥。每次导出都会生成一组新的配对密钥；整包由管理员保管，各设备只领取自己的目录。A 的防火墙决定允许转发的来源和目的。子网路由及回程设计可参阅 [Tailscale 子网路由说明](https://tailscale.com/docs/features/subnet-routers) 和 [WireGuard 官方快速入门](https://www.wireguard.com/quickstart/)。

验收时，在 B 用 C 局域网中另一台主机的原 IP 打开实际服务，例如 `https://192.168.20.42:8443`，再从 C 访问 B 局域网中的另一台主机。可另选 A 静态路由后的主机验证多网段访问。隧道场景先查看最近握手，再核对 A 的转发、回程和目标服务的监听地址。读取成功或导出完成仅表示配置已准备好。

## 指定服务转发

在「共享栏目 → 跨网互联 → 服务转发」新建规则，选择 DevKit 的安装位置，填写实际服务地址和 TCP 端口。「保存并检测」会检查当前安装位置可用的路径。选择通过检测的方式后启动入口，客户端使用原有的账号、协议和程序。

| DevKit 在哪里 | B 如何访问 C | 需要什么 |
| --- | --- | --- |
| 中转端 A | 连接 A 的监听 IPv4 和端口，由 A 连接指定的 C 服务 | B 能访问 A 的入口，A 能访问 C 的服务；A、B、C 均无需 VPN |
| 访问端 B | B 连接本机入口，如 `ssh -p 2222 user@127.0.0.1` | 能直达目标，或 A 已提供获准的 SSH 本地转发、HTTP CONNECT 或 SOCKS5 |
| 服务端 C | C 通过 SSH 在 A 申请入口，B 连接 A 的地址和端口 | C 可登录 A，A 接受反向转发并允许监听 B 可达的地址；B 能访问该端口 |

B、C 表示访问端与服务端。上述端口规则按访问方向配置。双方需要主动访问对方原 IP 时，选择下方的「原 IP 双向互通」。监听地址填客户端能访问的网卡 IPv4；访问端本机使用可填 127.0.0.1。对外监听时指定允许的来源 IPv4，经过 NAT 时填监听端实际看到的地址。规则可保存 64 项，重启后手动启动。独立服务与桌面使用相同转发实现。

## 原 IP 双向互通

在「共享栏目 → 跨网互联 → 原 IP 双向互通」新建一份方案，先填写三个 IP。A 是两边都连得上的设备，B 和 C 是想互相访问的两台设备。A 填平常登录它的地址，B、C 分别填希望对方访问的地址。桌面端点「检测并配置」。共享网页有编辑和检测权限时可点「识别并保存」；若需要登录 A 来查询，还须有局域网主机的 SSH 终端权限和已确认的 A 档案。只有编辑权限或识别不全时，可以保存草稿，在桌面打开「继续填写」接着做。DevKit 匹配本机安装位置和已核对指纹的管理档案，从 A 分别查询到 B、C 的实际直连路由及源地址。两侧独立判断，遇到经其他网关、选路不明确或缺少档案，会说明原因，保留已确定的地址并提示补充。可选「仅保存」先生成方案。此模式要求 A 能在两侧分别充当直连下一跳，端点地址唯一，沿途网络允许保留源 IP。若实际拓扑经过其他路由器，应由相应网关管理员配置去程和回程。

打开已保存的方案，可按 B、A、C 三行核对地址。「B 连接 A」指从 B 直接连接 A 时使用的 IP，「C 连接 A」同理。例如在 B 用 SSH 直连 user@192.168.1.10，这里的地址就是 192.168.1.10。两边用同一地址直接连接 A 时可以填同一个 IP。桌面端可在地址下方选择「一键配置」，各设备的手工配置与验证步骤可按需展开。本机使用当前系统权限，其余两台复用已确认指纹的 SSH 管理档案。检测发现缺档案时，桌面端在当前方案打开对应设备的表单，预填设备地址；填写用户名、密码，核对端口、目标系统和服务器管理员提供的 SHA256 主机指纹。登录验证成功后，密码加密保存到本机的主机档案库，自动继续检测或配置。已有待验证档案可以直接选用。DevKit 在 B 上补录 C 时，读取指纹、登录和保存档案均使用方案中已信任的 A；装在 C 上补录 B 同理。表单显示管理路径。已有经该 A 登记的对端档案可直接复用，原有直连档案保留。A 缺少档案时先补录 A；若有多个符合条件的 A 账号，先确认本次使用的账号。取消或登录失败可返回原方案。可复用管理员预先登记的跳板连接。首次需具备到每台设备的管理通道，Windows 使用管理员权限，Linux 使用 root 或允许非交互 sudo 的账号。没有管理权限时，可展开各设备的 Linux 或 Windows 步骤。共享网页可查看方案，系统变更由桌面发起。

DevKit 先检查三台设备的接口、权限、路由冲突和持久化条件，然后在 A 的指定接口启用 IPv4 转发，在 B 和 C 各保存一条目的为对方原地址的 /32 路由。Linux 端点支持由 NetworkManager 或 systemd-networkd 管理的接口，A 使用 sysctl.d。Windows 使用 NetTCPIP。等效配置会保留，写入失败会尝试撤回本次变更。A 启用的是接口级转发，流量继续受现场防火墙和网络 ACL 约束。公网 NAT、重叠地址或云平台源/目标检查可能需要网管处理。

完成后，B、C 分别用对方的原 IP 和原端口访问已开放服务。DevKit 退出后系统路由仍有效。配置后的新 TCP 或 UDP 服务沿用同一路由。可在 Linux 用 `ip route get 对端IP`、在 Windows 用 `Find-NetRoute -RemoteIPAddress 对端IP` 检查选路，再从双方分别访问实际服务。方案页提供本机检测和手工撤回说明，移除方案记录仅删除 DevKit 保存的数据。[Linux 内核转发选项](https://docs.kernel.org/networking/ip-sysctl.html) · [Windows 主机路由](https://learn.microsoft.com/en-us/powershell/module/nettcpip/new-netroute)

### 检查 B 和 C 是否能互访

在已完成的方案点「检测双向互通」。DevKit 在 B 上向 C 的原 IP 发起一次 ping，再单独从 C 检测 B，两行结果各自显示。远程设备使用已有的可信 SSH 管理档案；共享网页需要跨网互联的检测权限，使用远程档案还需要 SSH 终端权限。缺少权限、档案或管理连接时，对应方向会提示无法验证。此操作只做检测。

要确认某个服务能否连接，展开「检测服务端口（可选）」。例如，B 要访问 C 的 SSH，就在「B → C」填写 C 实际监听的 TCP 端口（通常是 22）；C 要访问 B 的 HTTPS 则在「C → B」填写 B 的 HTTPS 端口。只填关心的方向即可。即使 ping 没有应答，也会单独尝试指定的 TCP 连接。TCP 连通后，用实际客户端确认登录或业务响应。

如果双方 ping 都有应答，只有某个端口连不上，先核对目标设备上的服务是否启动、监听了正确的 IP 和端口，以及设备和中间防火墙是否允许该连接。新建互通方案只配置路由，不会启动服务或修改这些放行规则。

## 检测结果和处理

- **直达目标**会从 DevKit 主机连接指定的目标端口。如已在网络设备配置静态端口映射，可把映射入口作为目标。失败时，在目标设备使用 Linux 的 `ss -lnt` 或 Windows 的 `Get-NetTCPConnection -State Listen` 核对服务绑定，再按实际来源放行服务端口。
- **SSH** 检测与启动都使用「局域网主机」中匹配 A 的档案，并按其中配置的跳板链连接。只有缺少匹配档案时，检测才会尝试直读 A 的 SSH 协议标识以提示登记。首次连接请通过已有可信渠道核对主机指纹。SSH 能登录后，还会实际尝试连到指定的服务或申请反向监听。探测反向监听时拒绝数据连接，随即关闭探测会话。A 接受监听请求后仍需从 B 验证防火墙、绑定与 NAT。
- **HTTP CONNECT / SOCKS5**会分别在填写的端口与 A 协商，尝试连接指定目标。默认入口为 3128 和 1080，可在规则内修改。只检查这些入口；现场使用其他端口时请填写实际值。本版支持按来源授权的免口令代理，遇到 HTTP 407 或 SOCKS 认证要求时，使用受限来源策略或选用已有 SSH 档案。
- **现场配置**。每项结果可展开「如何配置和验证」，查看本规则对应的目标地址、端口及配置。A 缺少 SSH 服务时，可由管理员启用已有的系统 OpenSSH Server，核对服务监听和账号授权。如果现场禁止增加服务，可改用已有的代理或路由。在局域网内只能 ping 通 A，且现场既无可用转发又无法更改路由时，单端应用无法建立跨网通道。
- **直接按原始 IP 访问**需要去回路由。当 A 可承担三层网关时，由网络管理员在 B 侧添加去往 C 主机/子网的路由，下一跳指向 B 侧可达的网关；在 C 侧为 B 添加返回路由。在 A 按实际接口启用 IPv4 转发，并仅允许对应来源、目的和业务端口。各侧网关须能逐跳转发至 A。栏目中的端口转发不要求修改系统路由。
- **外端验证**。入口启动后，从实际访问端使用 `Test-NetConnection <入口地址> -Port <端口>` 或目标客户端连接。SSH/SFTP 使用目标服务器的账号及指纹。HTTPS 若依赖域名或 SNI，客户端应使用证书对应的主机名。
- **FTP**同时使用控制端口与数据端口。在服务器配置固定的被动端口范围，在规则中填写同一范围（每条规则最多 32 个连续数据端口）。DevKit 对数据端口同号转发。客户端使用 EPSV 或忽略 PASV 返回的不可达 IP，沿用控制连接的地址。沿途防火墙和 SSH/代理策略须同时允许数据端口。仅转发 TCP 21 只能建立控制连接。

例如 Windows A 已有端口代理功能，B 侧地址为 `192.168.10.5`、C 的服务为 `192.168.20.8:22`。A 的管理员可以添加并查看单项映射，再在防火墙中只向 B 的实际来源放行 TCP 2222。B 用 SSH 或 SFTP 访问 `192.168.10.5:2222`，C 允许 A 访问其 TCP 22。若需撤回，仅删除对应入口。[Windows 端口映射文档](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netsh-interface)

```text
netsh interface portproxy add v4tov4 listenaddress=192.168.10.5 listenport=2222 connectaddress=192.168.20.8 connectport=22
netsh interface portproxy show v4tov4
```

撤回该映射可使用 `netsh interface portproxy delete v4tov4 listenaddress=192.168.10.5 listenport=2222`。

## A 的 OpenSSH 配置示例

在 A 为转发专用账号设置权限。B 安装 DevKit、目标服务在 192.168.20.8:22 时：

```text
Match User devkit-forward
    AllowTcpForwarding local
    PermitOpen 192.168.20.8:22
```

C 安装 DevKit、B 使用 192.168.10.5:2222 作为入口时：

```text
Match User devkit-forward
    AllowTcpForwarding remote
    GatewayPorts clientspecified
    PermitListen 192.168.10.5:2222
```

核对账号、密钥的转发限制及 A 上实际存在的接口。先校验配置再重载服务，保留现有管理会话。登录 B 或 C 无需部署远程代理。服务转发模式的检测只验证目标和入口；系统路由由桌面的「原 IP 双向互通」模式单独配置。数据转发只使用规则指定的固定目标和已授权来源。

## 共享权限

`DEVKIT_SHARE_RELAY` 开放栏目，`DEVKIT_RELAY_EDIT` 允许维护规则，`DEVKIT_RELAY_CONTROL` 允许检测和启停。共享网页使用 SSH 凭据还需「局域网主机 → SSH 终端」权限。退出或撤销网页会话时会停止该会话建立的转发，桌面启动的转发随 DevKit 退出停止。旧 WireGuard 配置不自动创建监听或授予新权限。

SSH 连接复用项目已有 ssh2、档案与指纹校验。HTTP CONNECT 使用 Node HTTP 客户端，SOCKS5 使用随包分发的 MIT 许可 socks 客户端。与 3proxy 等独立代理服务相比，已有代理可直接复用，现场无需新装代理服务。[OpenSSH 转发选项](https://man.openbsd.org/sshd_config.5) · [ssh2](https://github.com/mscdex/ssh2) · [socks](https://github.com/JoshGlazebrook/socks) · [3proxy](https://github.com/3proxy/3proxy)
